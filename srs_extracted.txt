 Software Requirements Specification (SRS) Project Title CoU DineX Smart University Cafeteria, Food Ordering & Campus Delivery Management System Institution: Comilla University ( CoU ), Cumilla , Bangladesh System Type: Web-based Smart Food Ordering and Cafeteria Management System Primary Focus: Unique UI/UX, easy ordering, secure payment, real-time order tracking, campus-aware food delivery. 1. Introduction 1.1 Purpose The purpose of CoU DineX is to develop a smart web-based food ordering and cafeteria management platform for Comilla University. The system will allow university students, teachers, staff, and visitors to browse cafeteria menus, order food, make online payments, order from cafeteria tables using QR codes, receive food at university halls or departments, track orders, and receive real-time notifications. At the same time, cafeteria staff will be able to manage food, orders, tables, kitchen operations, inventory, payments, deliveries, and customer feedback through an administrative dashboard. The system will combine the convenience of modern food delivery applications with university-specific facilities. 2. Background Traditional university cafeterias generally depend on: Manual ordering → Cash payment → Verbal communication → Manual food preparation → Manual delivery This creates several problems: Long queues Crowded cafeteria Difficulty knowing available food Manual payment Order mistakes Lack of order tracking Difficulty managing tables No proper delivery system No centralized student information Poor inventory management Lack of useful analytics CoU DineX will digitize these processes. 3. Vision The main vision is: “Make university food ordering as simple as ordering from a modern food-delivery application, while keeping the experience specially designed for the university campus.” Core Flow Discover → Select → Order → Pay → Prepare → Track → Receive → Review 4. Project Objectives The major objectives are: To provide an online university cafeteria ordering system. To reduce cafeteria queues. To provide QR-based table ordering. To support online payment. To generate digital payment receipts. To provide food delivery to university halls. To provide food delivery to departments and academic buildings. To support student and visitor ordering. To provide real-time order status. To provide live delivery tracking. To provide cafeteria table management. To manage menu and food availability. To manage cafeteria inventory. To provide kitchen/sales order management. To provide secure authentication. To provide campus map integration. To provide group ordering and split payment. To provide smart queue management. To provide personalized food recommendations. To provide analytics for cafeteria administrators. To provide an attractive and user-friendly UI/UX. To improve overall university cafeteria efficiency. 5. Authentication Secure login Password hashing Email verification OTP where required Session management Password reset Authorization Role-based access control: Student Visitor Staff Manager Admin Each role has different permissions. 50. Admin 2FA Administrator login can require: Email + Password ↓ OTP / Authenticator ↓ Admin Dashboard This provides stronger protection for privileged accounts. 51. Data Security The system should use: HTTPS/TLS Encrypted credentials Secure API Input validation Parameterized database queries CSRF protection where applicable Rate limiting Secure session handling Audit logging 52. Payment Security The system must: Use trusted payment gateways. Verify payment server-side. Validate transaction IDs. Prevent duplicate payment processing. Never store raw card passwords/PINs. Store only necessary transaction information. 53. QR Security Each table QR should contain a secure identifier/token. Server validates: Is table valid? Is cafeteria active? Is QR token valid? Is table available? This prevents simple QR manipulation. 54. Fraud Prevention System should prevent: Duplicate orders Duplicate payments Fake transaction IDs Unauthorized admin access Fake delivery completion QR manipulation Repeated coupon abuse Important transaction operations should use unique IDs and server-side validation. 55. Privacy The system should follow: Minimum Data Principle Only collect information necessary for the service. For live delivery tracking: Location sharing starts → Delivery Location sharing ends → Delivery completed Student's continuous location history should not be collected unnecessarily. 56. Functional Requirements The SRS can define requirements using IDs. FR-01 — Registration The system shall allow students to register using valid university information. FR-02 — Login The system shall authenticate registered users securely. FR-03 — Visitor Access The system shall allow visitors to order using guest access. FR-04 — Menu The system shall display available food items. FR-05 — Search The system shall allow users to search for food. FR-06 — Cart The system shall allow users to add/remove/update food items. FR-07 — QR Table The system shall identify cafeteria tables through QR codes. FR-08 — Table Service The system shall allow table users to request staff services. FR-09 — Ordering The system shall allow users to place food orders. FR-10 — Group Order The system shall allow multiple students to participate in one group order. FR-11 — Payment The system shall support online payment. FR-12 — Receipt The system shall generate digital payment receipts. FR-13 — Kitchen The system shall send confirmed orders to the kitchen. FR-14 — Order Status The system shall provide real-time order status. FR-15 — Hall Delivery The system shall support delivery to approved halls. FR-16 — Department Delivery The system shall support delivery to approved university locations. FR-17 — Live Tracking The system shall provide live delivery tracking during active deliveries. FR-18 — Notification The system shall notify users about important order events. FR-19 — Inventory The system shall manage cafeteria inventory. FR-20 — Reviews The system shall allow customers to review orders. FR-21 — Complaints The system shall support complaint submission and management. FR-22 — Analytics The system shall provide operational analytics. FR-23 — Security The system shall enforce role-based access control. FR-24 — Audit The system shall maintain audit records for critical administrative actions. 66. Non-Functional Requirements Performance Normal pages should load quickly under normal network conditions. Availability The system should remain available during cafeteria operating hours. Scalability The architecture should support increasing numbers of: Students Orders Food items Delivery requests Usability A first-time student should be able to place an order without training. Reliability Payment and order information must remain consistent. Security Unauthorized users must not access protected resources. Maintainability The code should be modular and documented. Compatibility The web application should support: Chrome Edge Firefox Safari Android browsers iOS browsers 67.
